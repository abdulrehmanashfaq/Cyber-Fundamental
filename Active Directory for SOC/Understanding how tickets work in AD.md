# Study Notes: Understanding How Kerberos Tickets Work in Active Directory

## 1. Overview & Architectural Foundation
Active Directory Domain Services (AD DS) relies on **Kerberos Version 5 (RFC 4120)** as its default and primary authentication protocol. Unlike legacy protocols such as NTLM—which rely on challenge-response handshakes—Kerberos uses a **ticket-based system** powered by symmetric key cryptography and a trusted third party.

In an Active Directory domain, the trusted third party is the **Domain Controller (DC)**, which hosts the **Key Distribution Center (KDC)**.

### The Key Players in Kerberos:
1. **Client (Principal):** The user or computer account requesting access to a service.
2. **KDC (Key Distribution Center):** Runs on every Domain Controller and is divided into two distinct logical services:
   - **Authentication Service (AS):** Authenticates the client's identity and issues the **Ticket Granting Ticket (TGT)**.
   - **Ticket Granting Service (TGS):** Evaluates the client's TGT and issues a **Service Ticket (ST / TGS)** for the requested target resource.
3. **KRBTGT Account:** A built-in, disabled domain service account. The password hash (secret key) of the `krbtgt` account is known only to the KDCs in the domain and is used to encrypt and sign all TGTs.
4. **Target Service (Application Server):** The server or daemon hosting the resource (e.g., SMB/File Share, MSSQL Server, HTTP/IIS, LDAP) identified by a **Service Principal Name (SPN)**.

## 2. The Anatomy of Kerberos Tickets

Kerberos operates on two primary ticket types:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        TICKET COMPARISON                               │
├───────────────────┬────────────────────────────┬───────────────────────┤
│ Property          │ Ticket Granting Ticket     │ Service Ticket        │
│                   │ (TGT)                      │ (ST / TGS)            │
├───────────────────┼────────────────────────────┼───────────────────────┤
│ Issuing Component │ Authentication Service (AS)│ Ticket Granting (TGS) │
│ Encrypted With    │ KRBTGT Secret Key (Hash)   │ Target Service Secret │
│                   │                            │ Key (Account Hash)    │
│ Readable By       │ KDC Only                   │ Target Service Only   │
│ Client Can Read?  │ No (Opaque blob)           │ No (Opaque blob)      │
│ Purpose           │ Proves identity to KDC to  │ Proves identity to    │
│                   │ request service tickets    │ specific application  │
│ Associated Event  │ Event 4768                 │ Event 4769            │
└───────────────────┴────────────────────────────┴───────────────────────┘
```

### What is Inside a Ticket?
Both the TGT and the Service Ticket encapsulate critical metadata inside an encrypted envelope:
- **Client Identity (Username and Realm):** Identifies who owns the ticket.
- **Validity Timestamps:** `StartTime`, `EndTime`, and `RenewTill` (protects against replay attacks).
- **Session Key:** A unique, ephemeral cryptographic key generated by the KDC.
  - In a TGT: The **Logon Session Key** (shared between client and KDC).
  - In a TGS: The **Service Session Key** (shared between client and target service).
- **PAC (Privilege Attribute Certificate):** A Microsoft proprietary extension containing the user's **Security Identifier (SID)**, primary group SID, and all transitive domain security group memberships. The PAC contains two cryptographic signatures:
  1. **Server Signature:** Signed by the target service key.
  2. **KDC Signature:** Signed by the `krbtgt` key.

## 3. The Three-Legged Kerberos Authentication Flow

Authentication in Active Directory is accomplished across three discrete exchanges:
1. **AS Exchange (AS-REQ / AS-REP)** $\rightarrow$ Obtain TGT
2. **TGS Exchange (TGS-REQ / TGS-REP)** $\rightarrow$ Obtain Service Ticket
3. **AP Exchange (AP-REQ / AP-REP)** $\rightarrow$ Access Target Application

```text
               Active Directory Kerberos Authentication Flow

   [ Client ]                       [ KDC / DC ]                     [ Target Service ]
       │                                  │                                  │
       │  1. AS-REQ (Encrypted Timestamp) │                                  │
       ├─────────────────────────────────>│                                  │
       │                                  │                                  │
       │  2. AS-REP (TGT + Session Key)   │                                  │
       │<─────────────────────────────────┤                                  │
       │                                  │                                  │
       │  3. TGS-REQ (TGT + Authenticator)│                                  │
       ├─────────────────────────────────>│                                  │
       │                                  │                                  │
       │  4. TGS-REP (Service Ticket)     │                                  │
       │<─────────────────────────────────┤                                  │
       │                                                                     │
       │  5. AP-REQ (Service Ticket + Service Authenticator)                 │
       ├────────────────────────────────────────────────────────────────────>│
       │                                                                     │
       │  6. AP-REP (Mutual Authentication - Optional)                       │
       │<────────────────────────────────────────────────────────────────────┤
```

### Step 1: The AS Exchange (Authentication Service)
*Goal: Authenticate the user to the domain without transmitting their password across the wire.*

1. **AS-REQ (Client $\rightarrow$ KDC Port 88):**
   - The user inputs their username and password.
   - The workstation derives the user's secret key from their password (using Kerberos string-to-key salt algorithms like AES or NTLM).
   - **Kerberos Pre-Authentication:** The client encrypts the current system timestamp with their secret key (`PA-ENC-TIMESTAMP`) and transmits it in the `AS-REQ` alongside the requested domain and username.
2. **KDC Validation & AS-REP (KDC $\rightarrow$ Client):**
   - The KDC looks up the user's account in Active Directory and retrieves their stored secret key.
   - The KDC decrypts the timestamp. If valid (within the standard 5-minute clock skew threshold), pre-authentication succeeds.
   - The KDC generates:
     - An ephemeral **Logon Session Key**.
     - A **TGT** (containing user identity, PAC, and Logon Session Key), encrypted with the **`krbtgt` password hash**.
   - The KDC packs the Logon Session Key into an encrypted message (encrypted with the **user's password hash**) and returns it alongside the TGT in the `AS-REP`.
   - **Windows Event Log:** Recorded on the DC as **Event ID 4768** (*A Kerberos authentication ticket (TGT) was requested*).

---

### Step 2: The TGS Exchange (Ticket Granting Service)
*Goal: Obtain permission to access a specific network service without re-authenticating.*

1. **TGS-REQ (Client $\rightarrow$ KDC Port 88):**
   - When the user tries to access a resource (e.g., `\\fileserver.corp.local\share`), the client checks its memory cache for an existing Service Ticket. If missing, it contacts the KDC.
   - The client constructs an **Authenticator** (timestamp encrypted with the *Logon Session Key*).
   - The client transmits the **TGT**, the **Authenticator**, and the target service's **SPN** (e.g., `cifs/fileserver.corp.local`) in the `TGS-REQ`.
2. **KDC Validation & TGS-REP (KDC $\rightarrow$ Client):**
   - The KDC uses its `krbtgt` key to decrypt the incoming TGT.
   - It extracts the Logon Session Key and decrypts the Authenticator to confirm the ticket requester is the legitimate owner.
   - The KDC looks up the target SPN to find the associated account (e.g., machine account or service user account).
   - The KDC generates an ephemeral **Service Session Key**.
   - The KDC creates the **Service Ticket (ST / TGS)** containing client details, PAC, and Service Session Key, and encrypts it with the **target service account's secret key (password hash)**.
   - The KDC returns the Service Ticket and a copy of the Service Session Key (encrypted with the client's Logon Session Key) in the `TGS-REP`.
   - **Windows Event Log:** Recorded on the DC as **Event ID 4769** (*A Kerberos service ticket was requested*).

---

### Step 3: The AP Exchange (Application Presentation)
*Goal: Present the Service Ticket to the application for authorization and session establishment.*

1. **AP-REQ (Client $\rightarrow$ Target Server):**
   - The client sends the Service Ticket along with a new Authenticator (timestamp encrypted with the *Service Session Key*) to the application server.
2. **Server Validation & AP-REP:**
   - The application server decrypts the Service Ticket using its **own password hash**.
   - It extracts the Service Session Key and verifies the Authenticator.
   - The application parses the **PAC** to read the user's groups and permissions. **Crucially, the server does not need to contact the Domain Controller to authorize the user!**
   - If mutual authentication is required, the server responds with `AP-REP`.
   - **Windows Event Log:** Recorded on the target host as **Event ID 4624** (Logon Type 3 - Network).

## 4. Key Security Implications & Attack Surface

The Kerberos ticketing protocol relies on two foundational design properties that attackers actively exploit:

1. **Tickets are Encrypted Blobs Sent to the Client:**
   - Because the KDC sends encrypted tickets directly to the client machine, an attacker who intercepts or requests these tickets can take the encrypted ciphertext offline and perform dictionary or brute-force attacks against the underlying encryption key.

2. **The Two Fundamental "Roasting" Attacks:**
   - **Pre-Authentication Bypass $\rightarrow$ [AS-REP Roasting](file:///home/abdulrehman/Cyber-Material/Cyber-Fundamental/Active%20Directory%20for%20SOC/AS-REP%20Roasting.md):**
     If an account has `Do not require Kerberos preauthentication` set, anyone can send an `AS-REQ` with just a username and receive an `AS-REP` encrypted with that user's password hash.
   - **Service Ticket Abuse $\rightarrow$ [Kerberoasting](file:///home/abdulrehman/Cyber-Material/Cyber-Fundamental/Active%20Directory%20for%20SOC/Kerberoasting.md):**
     Any valid domain user can request a TGS Service Ticket for any registered SPN. The returned ticket is encrypted with that service account's password hash.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   KERBEROS TICKET ATTACK COMPARISON                    │
├──────────────────────┬────────────────────────┬────────────────────────┤
│ Vector               │ AS-REP Roasting        │ Kerberoasting          │
├──────────────────────┼────────────────────────┼────────────────────────┤
│ Exploited Phase      │ AS Exchange (AS-REP)   │ TGS Exchange (TGS-REP) │
│ Target Account       │ User accounts with     │ Service accounts with  │
│                      │ pre-auth disabled      │ an SPN configured      │
│ Required Privilege   │ None (only username)   │ Any valid domain user  │
│ Artifact Cracked     │ User password hash     │ Service account hash   │
│ Primary Event ID     │ Event 4768             │ Event 4769             │
│ Detailed Guide       │ [AS-REP Roasting.md]   │ [Kerberoasting.md]     │
```

## 5. Summary of Windows Event IDs for SOC Monitoring

When monitoring ticket activity across Domain Controllers and member servers, SOC analysts evaluate the following Event IDs:

| Event ID | Event Description | Log Location | SOC Significance |
| :--- | :--- | :--- | :--- |
| **4768** | A Kerberos authentication ticket (TGT) was requested | Domain Controller | Monitored for **AS-REP Roasting** (`PreAuthType=0`) and mass logon failures (`Result Code 0x18`, `0x12`). |
| **4769** | A Kerberos service ticket was requested | Domain Controller | Monitored for **Kerberoasting** (`TicketOptions`, `TicketEncryptionType=0x17`, high volume of SPN requests). |
| **4770** | A Kerberos service ticket was renewed | Domain Controller | Monitored for long-lived session hijacking and suspicious renewal chains. |
| **4771** | Kerberos pre-authentication failed | Domain Controller | Identifies failed logon attempts, password spray attacks, or expired credentials. |
| **4624** | An account was successfully logged on | Member Servers / DCs | Logon Type 3 indicates network access following ticket presentation (AP Exchange). |
